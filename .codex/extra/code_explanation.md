### Configuration and credential artifacts

- [bootstrap.properties](certify-service/src/main/resources/bootstrap.properties) sets application names `certify,certify-plugin`, the config-server URI, default profile `local`, port `8090`, and MVC servlet prefix `/v1/certify`.
- [application-local.properties](certify-service/src/main/resources/application-local.properties) contains local issuer/authentication settings, selected plugin and scan package, JDBC configuration, key manager settings, and status/ledger settings. [AppConfig.java](certify-service/src/main/java/io/mosip/certify/config/AppConfig.java) initializes keys at startup. Local settings include demonstration credentials and a PKCS12 keystore configuration.
- [farmer-local-config.json](certify-service/src/main/resources/credential-configurations/farmer-local-config.json) is a credential configuration API payload, containing a Base64-encoded Velocity VC template, contexts, types, scope, signing suite and key references. It is not a JSON Schema validator specification, and its presence in resources does not automatically register it in the database.
- [farmer.json](docker-compose/docker-compose-injistack/context/farmer.json) is a local JSON-LD context. A context defines semantic term mappings; it is distinct from a template, credential display metadata, or a JSON Schema.
- [inji-certify-openapi.yaml](docs/inji-certify-openapi.yaml) describes HTTP request/response schemas. The current [CredentialConfigurationDTO](certify-core/src/main/java/io/mosip/certify/core/dto/CredentialConfigurationDTO.java) is the source of truth when older prose examples disagree with API field names.
- The active template and signing metadata live in `credential_config`, represented by [CredentialConfig.java](certify-service/src/main/java/io/mosip/certify/entity/CredentialConfig.java) and [CredentialConfigRepository.java](certify-service/src/main/java/io/mosip/certify/repository/CredentialConfigRepository.java). [CredentialConfigController.java](certify-service/src/main/java/io/mosip/certify/controller/CredentialConfigController.java) exposes CRUD under `/credential-configurations`.
- HTML/SVG rendering artifacts, including [credential-template.html](docker-compose/docker-compose-injistack/config/credential-template.html) and [svg-template.json](certify-service/src/main/resources/svg-template.json), are separate from the Velocity credential payload template.

## End-to-End Credential Request Flow

For the default servlet prefix, a client posts to `http://localhost:8090/v1/certify/issuance/credential`.

1. **Authentication and request parsing.** [SecurityConfig.java](certify-service/src/main/java/io/mosip/certify/config/SecurityConfig.java), [AccessTokenValidationFilter.java](certify-service/src/main/java/io/mosip/certify/filter/AccessTokenValidationFilter.java), and its local-profile counterpart populate/request authentication state. [VCIssuanceController.java](certify-service/src/main/java/io/mosip/certify/controller/VCIssuanceController.java) accepts a `CredentialRequest` containing `format`, `proof`, and format-specific fields. The local filter substitutes fake claims and must only run in isolated development.
2. **Service choice.** With `mosip.certify.plugin-mode=DataProvider`, [CertifyIssuanceServiceImpl.java](certify-service/src/main/java/io/mosip/certify/services/CertifyIssuanceServiceImpl.java) implements `VCIssuanceService`. With `VCIssuance`, [VCIssuanceServiceImpl.java](certify-service/src/main/java/io/mosip/certify/services/VCIssuanceServiceImpl.java) delegates complete credential issuance to an external `VCIssuancePlugin` instead.
3. **Scope and holder proof.** The DataProvider service checks request validity and token activity, walks space-separated token scopes until it finds metadata matching scope, format and requested credential, then validates the nonce and holder proof using [ProofValidatorFactory.java](certify-service/src/main/java/io/mosip/certify/proof/ProofValidatorFactory.java). An arbitrary identity field in the HTTP body is not the provider lookup contract.
4. **Data fetch.** The service adds `accessTokenHash` to the parsed claims and calls the injected provider exactly as `dataProviderPlugin.fetchData(parsedAccessToken.getClaims())`. The SPI receives `Map<String,Object>` and returns `org.json.JSONObject`, throwing `DataProviderExchangeException` on failure. It receives the original claims, including the whole scope string, rather than a separate selected credential configuration or request DTO. Custom providers must explicitly resolve allowed scopes and authenticated identity.
5. **Template assembly.** The service selects the template key for `ldp_vc`, `vc+sd-jwt`, or `mso_mdoc`, adds issuer/template settings, holder binding (`_holderId`), provider fields, validity times (`validFrom`, `validUntil`), and optional credential ID/status. `CredentialUtils.toJsonMap` prepares values; it does not guarantee JSON escaping of interpolated strings. Provider output is merged into the template parameters, so a custom provider should return an allowlist of business fields and exclude internal names.
6. **VC formatting.** [CredentialFactory.java](certify-service/src/main/java/io/mosip/certify/credential/CredentialFactory.java) chooses [W3CJsonLD.java](certify-service/src/main/java/io/mosip/certify/credential/W3CJsonLD.java), [SDJWT.java](certify-service/src/main/java/io/mosip/certify/credential/SDJWT.java), or [MDocCredential.java](certify-service/src/main/java/io/mosip/certify/credential/MDocCredential.java). [VelocityTemplatingEngineImpl.java](certify-service/src/main/java/io/mosip/certify/vcformatters/VelocityTemplatingEngineImpl.java) looks up the DB configuration, Base64-decodes `vcTemplate`, evaluates Velocity and parses the result as JSON. It supplies `_issuer`, `_dateTool`, `_esc`, and optional rendering digest. Types/context/format identify JSON-LD templates; SD-JWT and mdoc use their respective `vct`/doctype lookup paths.
7. **Signing and records.** `createCredential` produces the unsigned payload; `addProof` receives algorithm, key-manager app/ref IDs, DID URL and crypto suite from the configuration. For legacy JSON-LD suites, [ProofGeneratorFactory.java](certify-service/src/main/java/io/mosip/certify/proofgenerators/ProofGeneratorFactory.java) selects a generator. [Ed25519Signature2020ProofGenerator.java](certify-service/src/main/java/io/mosip/certify/proofgenerators/Ed25519Signature2020ProofGenerator.java) uses URDNA2015 canonicalization and `SignatureServicev2.signv2` with key references, returning a `proofValue`. W3C Data Integrity suites use `KeymanagerByteSignerFactory` through `W3CJsonLD`. Status/ledger handling and auditing accompany issuance according to configuration.
8. **Response and verification.** The service converts `VCResult` into `CredentialResponse`. Discovery is exposed by [WellKnownController.java](certify-service/src/main/java/io/mosip/certify/controller/WellKnownController.java) at `/v1/certify/.well-known/openid-credential-issuer`, with DID/JWKS siblings. Reverse proxies can expose different public paths. Verification needs a resolvable DID/public key matching the actual signing key, plus the relevant contexts.

## Native Providers vs Dynamic Plugins

PostgreSQL has two different roles here. Certify's own JDBC/JPA persistence is built into the service. The credential-source connector named `PostgresDataProviderPlugin` is an **external data provider**, not a native Java implementation in this checkout. No `DataFetcher` SPI or in-tree PostgreSQL fetcher implementation was found. The applicable extension interface is `DataProviderPlugin`.

The packaging POM includes `postgres-dataprovider-plugin`, `mock-certify-plugin`, `mosip-identity-certify-plugin`, and the Sunbird integration. Local documentation demonstrates `PostgresDataProviderPlugin` and `MockCSVDataProviderPlugin`. An upstream [PostgreSQL plugin README](https://github.com/inji/digital-credential-plugins/blob/master/postgres-dataprovider-plugin/README.md) describes sharing Certify's database; it also contains older version/configuration examples. Its current branch is not proof of the exact `0.6.0` artifact's implementation. Inspect that artifact's source before relying on datasource internals, row cardinality, result-key casing or multi-scope selection.

Loading and registration are separate steps:

1. The service [pom.xml](certify-service/pom.xml) sets Spring Boot packaging layout `ZIP`, enabling the PropertiesLauncher model. `-Dloader.path=/absolute/path/to/plugins` adds external JARs at **process startup**. Docker uses `loader_path_env` and an `additional_jars` directory; the bundled image copies plugin JARs there.
2. `CertifyServiceApplication` component-scans the built-in packages and `${mosip.certify.integration.scan-base-package}`. A custom plugin needs an annotated Spring component in a scanned package, or another explicit Spring registration mechanism. Merely copying a JAR is insufficient.
3. Implementations can use `@ConditionalOnProperty` tied to `mosip.certify.integration.data-provider-plugin`. The property is a selector interpreted by the plugin's annotations; Certify does not reflectively instantiate an arbitrary class named by this string.
4. `CertifyIssuanceServiceImpl` autowires a single `DataProviderPlugin`. Ensure exactly one is active; absent or competing beans prevent a reliable startup.
5. Restart after changing the JAR set. There is no inspected hot-reload plugin registry or per-request classloader. A single provider can dispatch scopes internally, but selecting a different plugin per credential is not established by this SPI.

`pluginConfigurations` exists on the credential configuration DTO/entity. The inspected fetch call passes claims only, and no provider-configuration dispatch was found in the service code. Do not assume those maps are automatically injected into a custom fetcher's arguments.

Some prose guides retain removed issuer settings, old DB paths (`db_scripts/mosip_certify`), old DTO names or discovery URLs. Use the current Java DTO/controllers, actual `db_scripts/inji_certify` tree and the configuration API sample above when implementing.
